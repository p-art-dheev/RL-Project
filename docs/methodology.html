Project methodology · deep RL for edge–cloud scheduling

PACE: how the project works, step by step

A deep-RL scheduler that sends every task of a smart-city job to a camera box in Coimbatore, AWS Mumbai (near, carbon-heavy) or AWS Stockholm (far, almost carbon-free), in about 0.5 ms per decision. It is compared against the 2026 MERSEM paper.

Base paper: MERSEM (2026) RL lineage: DeepRM · DeepRM2 Data: MERSEM's own DAG dataset Algorithm: BC → PPO Testbed: AWS ap-south-1 + eu-north-1

3 · Inside one decision

What happens each time a task becomes ready. Steps 1–5 run live (about 0.5 ms in total); step 6 happens only during training in the simulator.

⟲ learning loop
PPO updates the policy from the reward

Example: an analytics task (class B)

The policy scores every candidate node with the same small network.

r = −[(1−w)·carbon per unit of work + w·(½ task-deadline penalty + ½ job-deadline penalty)]

w = how much the operator cares about deadlines vs carbon. It is an input to the network, so one trained policy serves every w.

4 · Results so far

Simulation on held-out jobs, testbed-sized topology, 10 paired seeds (lower is better everywhere). Carbon uses synthetic hourly grid profiles; real-AWS runs come next.

Honest caveat: without the shield, PACE misses 23% of analytics deadlines. The misses come from very large jobs that overload the 4-core green region, and held-out jobs are bigger than training jobs (median 25 vs 15 tasks).
