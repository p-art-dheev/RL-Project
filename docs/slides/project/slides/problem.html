The problem

In India, the nearest compute runs on the dirtiest grid

Edge · Coimbatore

Camera boxes

0 ms away, but slow (Raspberry-Pi class) and one task at a time

~560 gCO₂/kWh (IN-SO)

Fog · AWS Mumbai

Near region

~35 ms round trip, fast x86 + ARM instances

~680 gCO₂/kWh (IN-WE)

Cloud · AWS Stockholm

Green region

~160 ms round trip, small capacity we rent

~35 gCO₂/kWh (SE-SE3): 20× cleaner

Three kinds of smart-city work share it: A safety alerts from cameras (1 s deadline, some feeds may not leave India), B graph analytics DAGs (tight deadlines), C batch analytics (hours of slack). Neither "run local" nor "run green" is right for all of them.

Grid intensities: approximate annual means, synthetic hourly profiles in this version (Electricity Maps data can be plugged in). RTTs: planning values, replaced by measured ones on the testbed.

Why the problem exists: latency pulls work to Mumbai or the edge, carbon pulls it to Stockholm, and capacity in the green region is limited. On top, load is bursty, grid intensity changes hourly, nodes fail and runtimes are only estimates. A plan made 15 minutes ago is stale. That is why we want an online, adaptive scheduler.
