What the real testbed taught us

Three sim-to-real gaps, each measured, fixed and fed back into the twin

Servers waited on the network

Each task held a core for its whole HTTP round trip. Tasks are now sent when placed, so transfers overlap with compute: smoke-test alert misses 18% → 0%.

Two vCPUs are one core

On c7i-flex, two tasks at once each run 1.75× slower; on ARM t4g, 1.0×. Calibration now measures it, and the twin then predicted the next smoke test.

The network drifts

Upload time to Mumbai doubled over one evening. An online latency estimate now feeds every scheduler: PACE's misses 14.7% → 3.8%.

PACE was fine-tuned in the calibrated digital twin of this testbed, and each prediction was written down before the real run.

Gap 1: the first orchestrator held a server core during the upload, the input fetch and the reply, so Stockholm's two cores mostly waited on a 400 ms network; the simulator only counted computation. Gap 2: per-task timings showed 1.68 to 1.83 times longer compute when two tasks shared a c7i-flex.large, whose two vCPUs are hyperthreads of one physical core. Gap 3: the median frame upload to Mumbai went from 0.25 s to 0.55 s during a 1.6-hour run, independent of our own traffic; schedulers that trusted the static calibration missed alerts. The fix measures recent network time per region and adds the 90th percentile of the residual to every scheduler's estimate. Documents: results/testbed/E8_ANALYSIS.md and TWIN_PREDICTION.md.
