PACE: Viva Guide

Carbon- and SLA-aware edge–cloud scheduling with deep reinforcement learning · 22AIE401 Reinforcement Learning
Nandu Manoj · Naren Sundar L · Vatturu Pardheev · Charuvarthan T · Guide: Dr. Palmani Duraisamy

The project in 30 seconds Every job (for example a camera alert) is a small graph of tasks. For each task an RL agent chooses where to run it: on the camera box (edge), on a near server in Mumbai (fog, dirty coal power) or on a far server in Stockholm (cloud, clean power). Each choice trades meeting the deadline against carbon. Our agent, PACE, learns this trade-off by trial and error in a simulator (PPO), then runs on real AWS machines, deciding in about 1 ms per task. It beats the base paper, MERSEM.

Existing work vs our work

The base paper: MERSEM (Ramicetty et al., arXiv 2026)

Problem: the same as ours: schedule graph-analytics jobs on edge, fog and cloud so that few jobs miss deadlines and little carbon is emitted.

What they do, intuitively: every 15 minutes they predict the next 15 minutes of jobs, then run an evolutionary (genetic) algorithm that searches for a good "job → machine" plan. The RL part is small: a tabular Q-learning agent only chooses how strongly to mutate plans during the search (5 choices). Objective: a fixed weighted sum, score = ws·(miss rate) + wc·(carbon), with ws + wc = 1.

Dataset: the Rezaee & Adabi DAG workflow dataset (Zenodo, CC-BY-4.0): 51,895 jobs, 1.3 million tasks, typically 7–62 tasks per job, with task sizes, dependencies and deadlines. We use the same dataset: the first 70% of its timeline for training, the last 30% for all tests.

Evaluation: simulation only (extended EdgeCloudSim), against other metaheuristics (PSO-GA, GWO, ...).

Step 1The environment: what the agent lives in

In RL, the environment is everything outside the agent: it shows the agent a situation, accepts an action, moves forward in time and later says how good the outcome was. Ours is a discrete-event simulator of the edge–fog–cloud system (during training), or the real AWS testbed (when deployed). The agent cannot tell which one it is talking to: both use the same interface.

What the simulator models

  • Nodes with a number of CPU slots, a speed, a location and a grid zone. Busy nodes slow down a bit (CPU contention).
  • Network: moving data between places costs half a round trip plus size ÷ bandwidth.
  • Jobs arrive over time (alerts from cameras, analytics and batch DAGs from the dataset), each with a deadline.
  • Uncertainty: the agent only sees estimated task sizes (up to ±40% wrong); nodes can fail or slow down.
  • Carbon: energy used × the hour's grid carbon intensity of that node's region.

One episode, step by step

1. Start: build a random world (nodes, network, load) and pick a random preference w
↓
2. Time moves until something happens: a job arrives, a task finishes, a node fails
↓ a task's parents are all done → the task is "ready"
3. Decision point: the agent sees the state and picks a node (or defer)
↓
4. Simulate: send inputs over the network, wait for a slot, run, send output on
↓
5. When the job finishes: we know if it was late and how much CO₂ it used → rewards for its decisions
↓
6. Repeat for 20 simulated minutes of arrivals, then let the remaining work drain

Note the delayed reward: a placement's consequences are only known when its job finishes, maybe many decisions later. This is exactly the credit-assignment problem RL is built for.

Domain randomisation: a different world every episode

If the agent always trained in one fixed world, it would memorise it. So each episode draws a new one:

Step 2Turning scheduling into an RL problem

We describe the problem as a (semi-)Markov decision process: state, action, reward, and a transition (the environment of Step 1). "Semi" because decisions do not happen every fixed second but whenever a task becomes ready.

State s: what the agent sees

  • About the task (20 numbers): class, estimated size, time left until its sub-deadline (the "budget"), work still to do after it, privacy flag, how loaded the system is, time of day, how much work its whole job still has (job pressure), and the preference w.
  • About each candidate node (18 numbers): tier, speed, estimated transfer, wait, run and finish time, grid carbon now and in 1 h and 3 h, the task's estimated carbon there, current load, and "would it finish in time?".

Action a: what the agent can do

  • Pick one node for the task, or Defer it (only batch tasks with spare time, at most 3 times).
  • Masks remove illegal moves before the agent chooses: crashed nodes, nodes without memory, private data leaving India, another camera's box. The agent never wastes experience on impossible actions.

Reward r: what the agent is paid

  • Carbon cost of the task, weighted by (1 − w).
  • Lateness cost, weighted by w: half for missing the task's own sub-deadline, half for missing the job's deadline.
  • Rewards are negative (costs): the agent learns to make them as close to 0 as possible.
Key idea: deadline decomposition A big job has dozens of tasks. If we only punish the job at the end, the agent cannot tell which task caused the miss. So each task gets its own sub-deadline: job deadline − time still needed after this task. Now each decision is judged by what it controlled.

Goal

Maximise the sum of future rewards (the return). With γ = 0.8, rewards a few decisions ahead still count, but the agent focuses on the consequences of its own placement.

Step 3The agent (actor–critic) and the key formulas

Input per nodenode facts + task facts (incl. w)
→
Same small MLPfor every node (2 × 128)
→
One score per node+ a score for "defer"
→
Masked softmaxprobabilities of legal actions

Actor (the policy above) chooses actions. Critic (a second head) predicts how good the current state is, V(s), which PPO needs. Because the same network scores every node, it works with 6 nodes or 30, and a crashed node is just masked out (≈ 60 K parameters, ≈ 0.55 ms per decision).

① Return: what the agent maximises
G = r1 + γ·r2 + γ2·r3 + …   (γ = 0.8)
Total future reward, with later rewards counted a bit less.
② Reward for placing task i
r = − [ (1 − w)·carboni + w·( ½·latetask + ½·latejob ) ]
carbon is normalised so both parts have similar size. late = 0 if on time, otherwise 1 + how late (capped at 2).
③ Policy: probability of choosing node m
π(m | s, w) = ezm / Σlegal k ezk
Softmax over the scores of legal nodes. Training samples from it (exploration); deployment takes the most likely node.
④ Advantage: was the action better than expected?
δt = rt + γ·V(st+1) − V(st)    At = δt + γλ·δt+1 + (γλ)2·δt+2 + …
δ = "surprise" at one step. A (GAE, λ = 0.9) adds up the surprises that follow. A > 0: better than the critic expected.
⑤ PPO policy update: improve, but carefully
ratio = πnew(a|s) / πold(a|s)   LPPO = − min( ratio·A , clip(ratio, 0.8, 1.2)·A )
Make good actions (A > 0) more likely and bad ones less likely, but never change an action's probability by more than ±20% per update.
⑥ Full loss
L = LPPO + 0.5·(V(s) − G)2 − β·entropy
Policy + critic error − exploration bonus (β: 0.01 → 0.002).
⑦ Behaviour cloning (warm start)
LBC = − log π( CA-EFT's action | s )
First copy a good simple rule.
⑧ SLA controller (sets w live)
e = miss rate − target
w = w0 + 0.8·e + 0.08·Σe
Too many misses → w goes up. Like a thermostat (PI controller).
⑨ Safety shield
keep node if: time to finish ≤ (1 − 0.6w)·budget
At w = 1 a node must finish within 40% of the time left.
⑩ Carbon of a task
CO₂ = extra power × run time × grid intensity
Grid intensity makes Mumbai ≈ 20× dirtier than Stockholm.
⑪ Miss rate (main metric)
miss rate = (# A+B jobs late) / (# A+B jobs)
The same metric as MERSEM.

The training loop (one "iteration")

→
2Scorewhen jobs finish, give each decision its reward ②
→
3Judgecritic gives V(s); compute advantages A ④

4Update4 passes of PPO ⑤⑥ over the data in mini-batches
→
5Checkevery 3 iterations: 2 fixed validation runs vs CA-EFT

↻ repeat with the improved policy (82 iterations, ≈ 3.5 million decisions, ≈ 35 minutes on the laptop CPU)

Before this loop, 3 iterations of behaviour cloning ⑦ teach the agent to imitate CA-EFT. Starting from a random policy would be slow: random placements miss almost every deadline, so almost every reward would be bad and hard to learn from.

Final model. (a) reward per decision; (b) validation carbon; (c) validation alert misses; (b, c) at w = 0.75 vs the CA-EFT teacher.

What it learned, phase by phase

After cloning (iterations 0–3). Carbon ≈ the teacher's (0.32 vs 0.31 g). It behaves like CA-EFT: a safe start.
Fast gains (3–15). Carbon drops ≈ 40% (0.32 → 0.19 g) while alert misses stay at or below the teacher's. It discovers that flexible work (analytics, batch) can go to clean Stockholm instead of dirty Mumbai without missing deadlines.
Fine-tuning (15–82). Carbon flat at 0.17–0.18 g (−44% vs teacher); alert misses wobble around the teacher's 0.8%. It balances edge cases: busy hours, big DAGs, and when Stockholm is too far for a tight deadline.

Why is the reward curve (a) so noisy? Every episode is a different random world and a different w, so the reward level jumps between episodes. The trend (thick line) and the fixed validation runs (b, c) are what show learning. The agent at w = 0.75 accepts a few more analytics misses than its teacher in exchange for much less carbon: that is the trade-off it was asked to make.

Proof that PPO (not just copying) made the difference We tested the policy after cloning only: it matches CA-EFT (2.8% missed, 0.78 g) and gives identical results at w = 0 and w = 0.9: it ignores w. After PPO, w really controls the behaviour: w = 0 → 11.5% missed, 0.30 g; w = 0.9 → 1.3% missed, 0.39 g. At w = 0.9 PPO halved the carbon of the cloned policy and missed fewer deadlines.

Three sim-to-real gaps we found and fixed 1. Dispatch: the orchestrator held a CPU slot during each network call → tasks are now sent as soon as they are placed.
2. CPU contention: a 2-vCPU x86 server is really 1 physical core; two tasks at once ran 1.7–1.8× slower (the simulator assumed 1.15×) → now measured per node.
3. Network drift: the link to Mumbai slowed during the evening, so alerts sent there were late, and PACE lost to MERSEM in that first run → an online network estimate adds the recent 90th-percentile extra delay to every estimate.

Why PACE does better

Fewer misses than MERSEM (13.3% → 1.3%)PACE decides when each task is ready, using the queues right now. MERSEM's plan is made up to 15 minutes ahead, so under load or after a crash it is out of date (its misses grow fastest in the load plot). PACE also places tasks individually; forcing it to place whole jobs like MERSEM raised analytics misses to 51%.
Less carbon than bothThe reward taught it which work can afford the trip to clean Stockholm: flexible analytics and batch go north, urgent alerts stay near. CA-EFT uses one fixed safety margin for every task, so it plays safe and sends more work to dirty Mumbai.
One policy, any trade-offw is an input during training (random every episode), so the network learned the whole curve; the controller just moves along it.
Bigger network, new regionThe shared node scorer judges each node by its features (speed, delay, carbon), not by its identity, so new or extra nodes are just more rows.
Robust to noise and failuresTraining already contained noisy estimates and varied worlds; crashed nodes are masked and their tasks re-decided immediately.

Drawbacks, with reasoning (say these before they ask)

Large analytics jobs: plain PACE misses 23% vs CA-EFT's 6%(1) Alerts are 98% of decisions, so the learning signal is dominated by alerts. (2) Test DAGs are larger than training ones (median 25 vs 15 tasks): a distribution shift. (3) The reward charges a placement only for its own job, not for the queue it creates for other jobs, so the agent piles big jobs onto the small clean cloud. Fix: the shield brings it to 6%; next step: a reward term for delay caused to others.
Much slower network: 17% vs CA-EFT's 1.4%Training never saw delays above 1.5× normal. Outside that range the learned pattern "Stockholm is reachable in time" is wrong, and the agent keeps sending alerts there. CA-EFT recomputes finish times with a formula, so it adapts. Fix: wider network randomisation in training plus the online network estimate.
Real AWS: +15% carbon vs MERSEMAt w = 0.9 PACE is told deadlines matter most, so it spends some carbon to miss fewer (6/6 runs better on deadlines). MERSEM sits at a different point (less carbon, many more misses). The carbon difference is not statistically significant (p = 0.16).
First real run lost to MERSEMNetwork drift (Step 6): PACE trusted the calibrated delay to Mumbai. Fixed by the online estimate (E8b).
Simulator is optimisticReal misses were 1–5 points higher than the twin predicted: the campus network varies more than the simulated one.
LimitationsCarbon data is synthetic (built from real yearly averages; free hourly data for India was unavailable). Small testbed: 6 nodes, 3 seeds per load.

Likely viva questions, short answers

Q: What exactly is the environment? A discrete-event simulator of edge, fog and cloud nodes, network links and arriving DAG jobs (training), or the real AWS testbed (deployment). It shows the agent a task and its options, applies the choice, and returns rewards when jobs finish.

Q: Is it on-policy or off-policy? On-policy: PPO only learns from data collected by the current policy, then throws it away and collects new data.

Q: Why PPO and not DQN? Policy-gradient methods handle a changing set of legal actions (masks) and a variable number of nodes naturally, and PPO's clipping keeps training stable.

Q: How does it explore? During training actions are sampled from the softmax, plus an entropy bonus; at deployment it takes the most likely action.

Q: Why γ = 0.8? A placement mostly affects its own job; a short horizon makes credit assignment easier and training faster.

Q: Does it keep learning after deployment? No, the weights are frozen. Only w (via the controller) and the network estimate adapt live.

Q: Why behaviour cloning first? A random policy misses nearly every deadline, so it learns slowly. Copying CA-EFT is a good start; PPO then beats its teacher.

Q: What is new compared with MERSEM? Online task-level decisions, deep RL as the scheduler, one policy for all w with a live controller, failure handling, and real-machine tests.

Q: Is the comparison fair? Yes: same jobs and carbon traces; our MERSEM even gets a perfect prediction of the next 15 minutes and an EFT fallback for failures.

Q: How is carbon measured on AWS? AWS has no power meter, so: CPU time × published watts per vCPU × PUE × grid intensity (the same model as MERSEM).
