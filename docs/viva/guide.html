PACE: Viva Guide

Carbon- and SLA-aware edge–cloud scheduling with deep reinforcement learning · 22AIE401 Reinforcement Learning
Nandu Manoj · Naren Sundar L · Vatturu Pardheev · Charuvarthan T · Guide: Dr. Palmani Duraisamy

The project in 30 seconds Every job (for example, a camera alert) is a small graph of tasks. For each task, we have to choose where to run it: on the camera box itself (edge), on a nearby server in Mumbai (fog), or on a far server in Stockholm (cloud). Mumbai is close but runs on dirty coal power; Stockholm is far but runs on clean power. So every choice trades meeting the deadline against carbon emitted. We trained an RL agent, PACE, that makes this choice for every task in about 1 ms. It beat the base paper (MERSEM) in simulation and on real AWS machines.

1. Existing work vs our work page 2

The base paper: MERSEM (Ramicetty et al., arXiv 2026)

Problem they solve: the same one as ours: schedule graph-analytics jobs on edge, fog and cloud so that few jobs miss deadlines and little carbon is emitted.

What they do, intuitively: every 15 minutes, they predict which jobs will arrive in the next 15 minutes, then run an evolutionary (genetic) algorithm that searches for a good "job → machine" plan. The RL part is small: a tabular Q-learning agent only decides how strongly to mutate the plans during the search (5 choices). Their objective is a fixed weighted sum: score = ws·(SLA miss rate) + wc·(carbon), with ws + wc = 1.

Dataset they use: the Rezaee & Adabi DAG workflow dataset (Zenodo, CC-BY-4.0). We inspected it: 51,895 jobs and 1.3 million tasks, typically 7–62 tasks per job, with task sizes, dependencies and job deadlines. We use the same dataset (first 70% of the timeline for training, last 30% for testing).

How they evaluate: simulation only (an extended EdgeCloudSim), against other metaheuristics (PSO-GA, GWO, ...).

2. Our approach: PACE as an RL problem page 3

The RL loop in one picture
Environment: simulator during training · real AWS testbed when deployed
↓ a task becomes ready
State s: facts about the task + facts about every candidate node
↓
Agent (policy network): gives a probability to each node, plus "defer"
↓
Action a: run the task on node m (or defer a batch task)
↓ task runs, job finishes later
Reward r: minus (carbon used + penalty if late) → agent learns from it

State (what the agent sees)

  • Task: its class, size, how much time is left (budget), how much work remains after it, whether it is private, and the weight w.
  • Each node: tier, speed, estimated wait, transfer and finish time, grid carbon now and forecast, the task's estimated carbon there, load.

Action (what it can do)

  • Pick one node, or Defer (only batch jobs with spare time).
  • Masks remove illegal choices: crashed nodes, private data going abroad, other cameras' boxes.

Reward (what it is paid for)

  • Lose points for carbon (scaled by 1 − w).
  • Lose points for lateness (scaled by w): half for the task's own sub-deadline, half for the whole job's deadline.
Key idea: deadline decomposition A big job has dozens of tasks. If we only punish the job at the end, the agent cannot tell which task caused the miss. So each task gets its own sub-deadline = job deadline − time still needed after it. Now each decision is judged fairly. Before this fix, the agent ignored w and missed 45% of analytics deadlines.

The policy network (why it works for any number of nodes)

Input per nodenode facts + task facts (incl. w)
→
Same small MLPfor every node (2 × 128 units)
→
One score per node+ a score for "defer"
→
Masked softmaxprobabilities over legal actions

Because the same network scores every node, it works with 6 nodes or 30, and a crashed node is simply masked out. It has about 60,000 parameters and decides in about 0.55 ms. A separate critic estimates how good the state is (needed for PPO).

At deployment: two extra safety layers

  • SLA-target controller: the operator says "at most 5% missed". If misses go up, the controller raises w; if there is headroom, it lowers w to save carbon. No retraining, because w is just an input.
  • Safety shield: before the agent chooses, remove nodes that clearly cannot finish the task in time.

3. The important formulas, explained simply page 4

① Return: what the agent maximises
G = r1 + γ·r2 + γ2·r3 + …    (γ = 0.8)
Total reward from now on, with future rewards counted a bit less. γ = 0.8 is small on purpose: a placement mostly affects its own job.
② Our reward for placing task i
r = − [ (1 − w) · carboni + w · ( ½·latetask + ½·latejob ) ]
carboni is the task's CO₂, normalised so both parts have similar size. late = 0 if on time, otherwise 1 + how late (capped at 2). w = 1: only deadlines matter; w = 0: only carbon matters.
③ Policy: probability of choosing node m
π(m | s, w) = ezm / Σlegal k ezk
Softmax over the scores z of the legal nodes only (masked). At deployment we simply take the node with the highest probability.
④ Advantage: was this action better than usual?
A = (return actually obtained) − V(s)
V(s) is the critic's guess of the return from this state. A > 0: the action was better than expected, so make it more likely. We use GAE (λ = 0.9), a smoothed version of this.
⑤ PPO update: improve, but not too much at once
ratio = πnew(a|s) / πold(a|s)    LPPO = − min( ratio·A , clip(ratio, 0.8, 1.2)·A )
Increase the probability of good actions (A > 0) and decrease bad ones, but the clip stops the policy changing by more than ±20% per update. This keeps training stable.
⑥ Full training loss
L = LPPO + 0.5·(V(s) − G)2 − β·entropy
Policy part + critic error (learn V) − an entropy bonus that keeps the agent exploring early on (β goes from 0.01 down to 0.002).
⑦ Behaviour cloning (warm start before PPO)
LBC = − log π( action CA-EFT would take | s )
First copy a good simple rule, so PPO does not start from random placements that miss almost every deadline.
⑧ SLA controller (sets w live)
e = miss rate − target
w = w0 + 0.8·e + 0.08·Σe
Too many misses → e > 0 → w goes up. A "PI controller", like a thermostat.
⑨ Safety shield
keep node if: time to finish ≤ (1 − 0.6w)·budget
At w = 1, a node must finish within 40% of the remaining time to be allowed.
⑩ Carbon of a task
CO₂ = extra power × run time × grid intensity
Grid intensity (g/kWh) is what makes Mumbai ≈ 20× dirtier than Stockholm.
⑪ SLA miss rate (main metric)
miss rate = (# A+B jobs late) / (# A+B jobs)
The same metric MERSEM uses.

Three sim-to-real gaps we found and fixed (good viva story) 1. Dispatch: the orchestrator held a CPU slot during each network call → now tasks are sent as soon as they are placed. 2. CPU contention: a 2-vCPU x86 server is really 1 physical core; two tasks at once ran 1.7–1.8× slower → now measured per node. 3. Network drift: the link to Mumbai got slower in the evening, so alerts sent there were late → we added an online network estimate (add the recent 90th-percentile extra delay to every estimate).

RL ablation: behaviour cloning alone just copies CA-EFT (2.8%, 0.78 g) and ignores w. PPO is what makes w work: from w = 0 to 0.9, misses fall 11.5% → 1.3% while carbon rises only 0.30 → 0.39 g.

Positives
  • Far fewer deadline misses than the base paper, with less carbon (simulation)
  • Fast: ≈ 1 ms per decision, reacts instantly to crashes and rush hours
  • One network for every trade-off; the SLA target can change live
  • Works on bigger networks and a new region without retraining
  • Tested on real machines, not just simulation
Negatives (say these before they ask)
  • Large analytics jobs: plain PACE misses 23% vs CA-EFT's 6% (the shield fixes most of it)
  • Very slow network outside training: 17% vs CA-EFT's 1.4%
  • On real AWS, PACE used 15% more carbon than MERSEM (not significant)
  • Carbon data is synthetic (built from real yearly averages)
  • Small testbed: 6 nodes, 3 seeds per load

Likely viva questions, short answers

Q: Why RL and not a simple rule? The best choice depends on many changing things (queues, carbon, network, DAG). A rule like CA-EFT must be re-tuned when goals change; our one policy covers every w and still uses 15–47% less carbon than CA-EFT.

Q: Why PPO? Stable (clipped updates), works with large discrete action sets and masks, and is the standard choice for policy-gradient training in simulators.

Q: Why behaviour cloning first? A random policy misses almost every deadline, so it learns slowly. Copying CA-EFT gives a sensible start; PPO then improves on its teacher.

Q: What is new compared with MERSEM? Online task-level decisions, deep RL as the scheduler, one policy for all w plus a live controller, failure handling, and real-machine validation.

Q: Is comparing with MERSEM fair? We were generous: our MERSEM sees the actual next-epoch jobs (perfect prediction) and falls back to EFT on failures. Everyone gets the same jobs and carbon traces.

Q: Why does PACE fail on the slow network? That network is far outside what it saw in training; CA-EFT simply recomputes finish times. Fix: wider network randomisation in training plus the online network estimate.

Q: How do you measure carbon on AWS? AWS gives no power meter, so: CPU time × published watts per vCPU × PUE × the grid's carbon intensity (the same model as MERSEM).
